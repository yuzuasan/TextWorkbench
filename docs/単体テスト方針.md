# 単体テスト方針

## 1. 目的

本資料では、TextWorkbenchにおける単体テストの作成対象、優先度、テスト内容および作成目標を定める。

単体テストの主な目的は、今後の機能追加や修正によるデグレード（既存機能の不具合・品質低下）を防止することである。

開発者個人による継続的な開発を想定し、特にアプリケーションの動作やデータの整合性に影響する処理を優先してテストする。

## 2. 基本方針

- テストフレームワークには **xUnit** を使用する。
- Domain、Application、Infrastructureを中心にテストを作成する。
- Presentationについては、UIに依存しない状態管理やロジックを中心にテストする。
- 正常系だけでなく、異常系、境界値、処理失敗時の状態維持も確認する。
- 外部サービスや依存コンポーネントは、必要に応じてFakeを使用してテスト対象から分離する。
- UI操作を伴うテストや統合テストは、本方針における作成対象外とする。
- カバレッジの数値目標は設定せず、重要な処理やデグレードの影響が大きい処理を優先する。

## 3. 単体テスト作成対象と優先度

テスト対象を以下の3段階に分類する。

- **高：必ず作成する。** アプリケーションの主要機能やデータの整合性に直結する処理。
- **中：重要なものを選択して作成する。** 品質向上やデグレード防止に有効だが、優先度「高」ほど必須ではない処理。
- **低：原則として作成しない。** UI表示や単純な処理など、単体テストによる効果が限定的なもの。

### 3.1 優先度「高」：必須作成対象

| テスト対象 | 主なテスト内容 |
|---|---|
| Document | 初期値、FilePath・Encoding・LineEndingの更新、IsModifiedの変更、IsReadOnly・IsLoading・IsSavingの状態管理、IsEditableの判定、編集時の状態変更、保存成功時の状態変更、操作のガード条件 |
| Workspace | Documentの追加・削除、Document一覧の管理、ActiveDocumentの切り替え、アクティブなDocumentの整合性 |
| EncodingService | 文字コードの判定、文字コードの取得・変換、BOMの扱い、対応する文字コードの正常系・異常系 |
| LineEndingService | CRLF・LF・CRの判定、改行コードの変換、混在した改行コードの扱い |
| SearchService | 通常検索、複数一致、0件、大小文字の扱い、正規表現検索、無効な正規表現、Multiline、Capture Group、ゼロ幅一致、タイムアウト |
| ReplaceService | Replace First、Replace All、通常文字列の置換、正規表現置換、Capture Group、置換件数、置換結果、連続Replace Next、置換時のDocument状態変更 |
| DiffService | 差分エンジンの結果からDomainモデルへの変換、Unchanged・Added・Deleted・Changedの扱い、DiffLine・DiffSegmentの変換、DiffCount、行番号がnullの場合、文字単位Segment |
| OpenDocumentUseCase | ファイル読み込み成功、読み込み失敗、例外発生時の処理、Documentの状態変更、読み込み失敗時に不正なDocument状態を残さないこと |
| SaveDocumentUseCase | 保存成功、保存失敗、例外発生時の処理、保存後のIsModified、保存失敗時に未保存状態を維持すること |
| SaveDocumentAsUseCase | 別名保存成功、保存失敗、保存先変更、保存後のDocument状態、保存失敗時の状態維持 |
| CloseDocumentUseCase | Documentを閉じる処理、未保存Documentの確認処理、閉じることができない場合の状態維持 |
| ExitApplicationUseCase | 終了確認、未保存Documentがある場合の処理、終了キャンセル時の状態維持 |
| CompareDocumentsUseCase | 差分比較の実行、比較対象の受け渡し、比較失敗時の処理、差分結果の取り扱い |

#### 優先度「高」の補足

- Documentはアプリケーション全体で使用する中心的なモデルであるため、状態管理と操作条件を重点的に確認する。
- SearchService・ReplaceServiceは、検索結果や置換結果に影響する境界値・正規表現の挙動も確認する。
- DiffServiceは、差分エンジンそのものではなく、差分結果をDomainモデルへ変換する処理を中心にテストする。
- UseCaseはFake Serviceを注入し、外部処理の成功・失敗を制御して検証する。
- 保存や読み込みに失敗した場合、Documentの状態やWorkspaceの内容が不整合にならないことを重視する。

### 3.2 優先度「中」：重要なものを選択して作成

| テスト対象 | 主なテスト内容 |
|---|---|
| FileService | ファイルの読み込み・書き込み、存在しないファイル、アクセス失敗、読み書き時の例外、保存結果 |
| TextInfoService | 行数、文字数、バイト数の計算、Unicode文字の扱い、UTF-8・UTF-8 BOM・Shift-JIS、CRLF・LF・CR |
| GetTextInfoUseCase | TextInfoServiceへの処理委譲、対象Documentの情報取得、結果の受け渡し |
| NewDocumentUseCase | 新規Documentの作成、初期状態、Workspaceへの追加 |
| SearchTextUseCase | 検索処理の呼び出し、検索条件の受け渡し、検索結果の反映 |
| ReplaceTextUseCase | 置換処理の呼び出し、置換結果の反映、Document状態の更新 |
| DiffTabViewModel | CurrentDiffIndex、Next・Previous、先頭・末尾の境界条件、差分0件、循環しないこと |
| DocumentTabViewModel | Documentの状態反映、編集状態、コマンドの実行可否、Documentとの状態整合性 |
| MainWindowViewModel | ActiveTabの切り替え、タブの追加・削除、DocumentとDiffの切り替え、Command CanExecute、Command状態更新 |

#### 優先度「中」の補足

- FileServiceは実ファイルを使用する必要がある場合、テスト用の一時ディレクトリを利用する。
- TextInfoServiceは、文字コードや改行コードによって計算結果が変わるため、代表的な組み合わせを確認する。
- ViewModelは、画面表示そのものではなく、状態管理やコマンドの実行可否など、UIに依存しないロジックを対象とする。
- 中の対象はすべてを一律に作成するのではなく、開発時の変更頻度や不具合発生時の影響を考慮して選択する。

### 3.3 優先度「低」：原則として作成しない

| テスト対象 | 対象外とする理由・補足 |
|---|---|
| WPF View | UI表示やレイアウトが中心であり、単体テストの対象としない |
| AvalonEdit Behavior | エディタ操作やUIとの連携が中心であるため、原則対象外とする |
| DocumentView | UI表示が中心であるため、原則対象外とする |
| Diff表示用View | 差分表示のUI部分は対象外とする |
| WPF FileDialogService | OSのファイルダイアログとの連携が中心であるため、対象外とする |
| MessageBoxNotificationService | MessageBox表示が中心であるため、対象外とする |
| MessageBoxConfirmationService | MessageBoxによる確認処理が中心であるため、対象外とする |
| App.xaml.cs / Composition Root | DI登録やアプリケーション起動時の構成が中心であるため、対象外とする |
| 単純なプロパティ取得・設定だけのクラス | 独自のロジックや状態変更がない場合、テストによる効果が限定的であるため対象外とする |
| DiffPlexAdapter | DiffPlexとの実際の接続・変換確認は統合テストに該当するため、今回の単体テスト対象外とする |

#### 優先度「低」の補足

優先度「低」は、今後もテストを作成しないことを保証するものではない。

不具合が発生した場合や、複雑なロジックが追加された場合には、必要に応じてテスト対象へ追加する。

## 4. 作成目標

単体テストは、以下の段階で作成する。

### 第1段階：優先度「高」の全対象

優先度「高」に分類した対象について、すべて単体テストを作成する。

特に、Documentの状態管理、ファイルの読み書き、検索・置換、差分比較、Documentの開閉・保存処理を重点的に確認する。

### 第2段階：優先度「中」の重要な対象

優先度「中」のうち、デグレード防止への効果が高いものを追加する。

追加候補は以下のとおり。

1. TextInfoService
2. FileService
3. DiffTabViewModel
4. DocumentTabViewModel
5. MainWindowViewModelの状態管理・Command CanExecute

そのほかの中分類対象についても、実装内容や変更頻度を考慮し、必要性が高い場合は追加する。

### 第3段階：優先度「低」の対象

原則として作成しない。

ただし、実装変更によって重要なロジックが追加された場合や、単体テストによる不具合防止効果が高いと判断した場合は、対象に追加することを検討する。

**最終的な作成目標は「優先度：高をすべて作成し、中のうち重要なものを追加する」とする。**

## 5. テスト対象に関する補足方針

### 5.1 Domain

- Domain層のモデルやロジックは、外部依存を持たない単体テストを基本とする。
- Documentのようにアプリケーション全体で利用されるモデルは、状態変更や操作条件を重点的に確認する。
- Domain層はWPF、AvalonEdit、DiffPlexなどの具体的な技術に依存しない構成を維持する。

### 5.2 Application

- ServiceやUseCaseは、Fake Serviceを注入してテストする。
- 外部処理の成功・失敗を制御し、UseCase自身の処理や状態変更を検証する。
- 正常終了だけでなく、例外発生時や処理失敗時の状態維持も確認する。
- Application層はWPF View、AvalonEdit、DiffPlexの具体型に依存しない構成を維持する。

### 5.3 Infrastructure

- 文字コードや改行コードなど、変換ロジックを持つServiceは単体テストの対象とする。
- ファイル操作をテストする場合は、一時ファイルや一時ディレクトリを利用し、テスト間でデータが干渉しないようにする。
- 外部ライブラリとの実際の接続確認は、単体テストと区別する。

### 5.4 Presentation / ViewModel

- ViewModelは、UI表示ではなく状態管理やコマンドの実行条件などを対象とする。
- ActiveTab、Documentの状態、差分表示の選択状態など、アプリケーションの動作に関係するロジックを確認する。
- WPF ViewやAvalonEditの操作そのものは対象外とする。
- ViewModelから直接ファイルI/OやDiffPlex APIを呼び出さない設計を維持する。

### 5.5 正常系・異常系・境界値

各テスト対象について、処理の性質に応じて以下を確認する。

- 正常な入力による期待どおりの処理結果
- nullや空文字などの不正・特殊な入力
- 対象データが存在しない場合
- 0件や1件などの境界条件
- 外部処理が失敗した場合
- 例外が発生した場合
- 処理失敗後に状態が不整合にならないこと

すべての項目を機械的に適用するのではなく、各処理に必要なケースを選択する。

### 5.6 テストの独立性

- テストケース同士が実行順序に依存しないようにする。
- 必要なテストデータは各テストで準備する。
- Fakeやテスト用データを活用し、外部環境への依存を可能な限り減らす。
- ファイル操作を伴うテストでは、一時ファイルを適切に後片付けする。

## 6. 今回の対象外

本方針では、以下を単体テスト作成の対象外とする。

- WPF画面の表示確認
- ボタンやメニューなどのUI操作確認
- AvalonEditの実際の編集操作
- WPF ViewとViewModelを組み合わせた画面全体の動作確認
- DiffPlexとの実際の接続確認
- アプリケーション全体を起動して行う動作確認

これらはUIテストまたは統合テストに該当するため、今回の単体テスト作成範囲には含めない。

## 7. まとめ

本プロジェクトの単体テストは、開発時のデグレード防止を目的として、重要なロジックと状態管理を優先して作成する。

- 優先度「高」は全対象を作成する。
- 優先度「中」は重要な対象を選択して追加する。
- 優先度「低」は原則として作成しない。
- xUnitを使用し、Fake Serviceなどを活用して単体で検証する。
- 正常系だけでなく、異常系・境界値・失敗時の状態維持も確認する。
- UIテストおよび統合テストは今回の対象外とする。

以上をTextWorkbenchの単体テスト作成方針とする。
